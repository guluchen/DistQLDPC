## #1 / H-003 reconsidered: verified input witness through existing initUB

Hypothesis: a cheap valid Pauli witness limits unnecessarily large upper-bound
probes without changing CNF topology. This is the previously untested candidate,
re-ranked using fresh evidence; it has no FIFO priority from Brain Round 1.

One mechanism: inspect original Gz rows as pure-X operators and original Gx rows
as pure-Z operators, validate each against the original stabilizer checks and
the exact nonzero logical-syndrome predicate, select the smallest verified
Pauli weight with deterministic ties, and supply that scalar through existing
`initUB`. No row reduction, witness search/local improvement, branching change,
or benchmark ground-truth lookup. No valid witness means the original path.

Code anchors: `src/core/distqldpc.cc:439` currently sets initUB to INT32_MAX;
`src/solver/Solver.cc:6626` converts it to a search-domain cap with a +1;
`:6761` applies the provided cap when raising a bound. Original row-XOR must be
absent in the trial. The cap is not proof of optimality and is not permission to
set `bestSolutionFound`, report an unsearched model, or certify a lower bound.

Read-only committed-input screen validates all 320 logical rows across six
pilot/Tier 1/Tier 2 datasets. Smallest verified weights:

| Case | Witness weight |
|---|---:|
| LP_136_32_4 | 6 |
| BB_90_8_10 | 10 |
| GB_144_12_8 | 8 |
| BB_108_8_10 | 12 |
| LP_238_44_6 | 6 |
| LP_340_56_8 | 14 |

These are feasible upper bounds derived solely from actual vectors, not known
distances fed to the solver and not runtime gains. Full vectors/input SHA-256s:
[screen receipt](raw/round2-witness-screen.json); reproduce with
`python optimization/brain/witness_screen.py`. No solver or Tier 2 was run.

Expected cases: both OFF/MTO when existing UB exploration exceeds a useful
witness cap. Headroom is unknown: initUB does not skip the initial UB=1 proof,
and the baseline may already find a model before the cap matters. Risk is
medium: residual-cost offsets, strict UB semantics, simplification and timeout
best-model reporting need an audit. Never subtract Pauli components separately
for mixed X/Z; this first scope uses pure operators only.

Falsification: cap never affects the bound sequence; added validation costs more
than saved search; wrong distance/bound/result status; any serious per-case
regression. Tier 0 requires original-CNF equality, witness truth tables, exhaustive
tiny CSS oracle, invalid/no-witness fallback and forced timeout checks with and
without an actually discovered solver model. Then unchanged Tier 1 across both
modes. Preparation effort moderate; Tier 0/Tier 1 normally minutes, same existing
worst-case limits, no large witness sweep. Do not proceed if bound semantics
cannot be established. Recommended #1 because useful witnesses already exist
and it targets search cost without repeating E001's encoding transformation.

## #2 / H-005: prefetch clauses in lookahead propagation

Hypothesis: ahead-of-use prefetch of long-clause headers in `propagateForLK`
reduces memory waits at the same logical search work. Observed lookahead/UP
counters justify investigating this path, but there is no measured cache-miss
profile; the bottleneck remains a hypothesis.

One mechanism: one fixed, preregistered prefetch distance in the long watcher
loop (`src/solver/Solver.cc:3959`), after normal watcher cleanup. Preserve loop
order, blockers, implication/reason selection, lastPoint, trail and conflict
accounting. No watcher representation change, binary fast-path rewrite,
restart/branching change or compiler-flag sweep. The engine already has separate
binary watches and circular lastPoint scans; proposing those again would not
be a new optimization.

Expected cases: lookahead-heavy solves in either mode if clause access is
memory-latency limited. Small/cache-resident cases may worsen. Risk low-to-medium:
cache pollution, address calculation overhead, invalid/out-of-range/relocated
clause references. Validate generated address expressions: prefetch itself being
non-faulting does not make an unsafe address expression valid. GCC's supported
primitive is documented in [Other Builtins](https://gcc.gnu.org/onlinedocs/gcc-13.1.0/gcc/Other-Builtins.html).
That document establishes the API, not a DistQLDPC speedup.

Falsification: sanitizer/reference-lifetime issue, changed logical propagation
outcomes, no beyond-noise gain or a serious case regression. Tier 0 includes
backtracking/deletion/GC propagation differential checks, unchanged original CNF,
tiny CSS/pilots and timeout reporting. Compare existing search counters on
completed runs; investigate unexplained differences. A short read-only baseline
profile is appropriate before implementation, and must not be confused with an
accepted optimization or used to tune many distances on evaluation cases.
One minimal patch and unchanged Tier 1; practical effort low-to-moderate.
Update MODIFICATIONS.md/NOTICE as required if implemented under src/solver.

## #3 / H-006: reuse a compatible MTO counting tree when tightening k

Hypothesis: avoid reconstructing the MTO counting network when only the bound
comparator changes. Current `addCardinalityConstraints` deletes cardinality
clauses and dynamic variables on a changed UB (`Solver.cc:6207`), and
`addCardinalityConstraintsMTO` rebuilds with `nLevelsMTO` (`:6275`).

One mechanism: retain the existing MTO tree only for the identical ordered active
literal list, compatible output width and a monotonically tighter bound.
Regenerate/update only the bound comparison. Any active-list/root-assignment,
width or bound-relaxation incompatibility takes the original rebuild path.
No new encoding family, switching OFF/MTO modes, Sinz rewrite, UB heuristic or
learned-clause retention policy is bundled. Actual reuse opportunities are
unmeasured and could be rare.

Expected cases: MTO mode with repeated compatible updates; OFF should be
unchanged. High correctness/engineering risk: retained units, learned reasons,
dynamic-variable recycling and GC relocation must remain valid; old tighter
constraints must never survive a relaxation. Scope feasibility can fail before
any implementation if the current lifecycle cannot support safe reuse alone.
Incremental cardinality reuse has a research precedent, but those published
MaxSAT algorithms are not this downstream solver, and do not prove this patch:
[Martins et al., 2014](https://arxiv.org/abs/1408.4628).

Falsification: no compatible repeated trees, construction is negligible, worse
whole-solve time, or any stale-constraint/semantic mismatch. Tier 0 needs
exhaustive assignment projection for sequences of tightening, loosening, list
changes and width boundaries, plus deletion/GC/backtracking and ordinary
CSS/pilot/timeout checks. Then both-mode Tier 1 without pooling away OFF
regressions. Effort high, so rank third; first inspect lifecycle/reuse counts.
Update engine modification notices if implemented.
