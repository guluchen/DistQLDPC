## H-010: PGO only

Hypothesis: execution profiles improve branch/layout/inlining decisions enough
to reduce runtime in the unchanged solver. The baseline Makefile uses `-O3`
without profile feedback. This is ordinary compiler optimization, supported by
[GCC profile-use documentation](https://gcc.gnu.org/onlinedocs/gcc-14.4.0/gcc/Optimize-Options.html#index-fprofile-use)
and [instrumentation documentation](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html).
No MaxSAT paper is claimed as its origin. PGO is distinct from E004 LTO.

Scope: one profile-generation/training/profile-use build workflow; same source,
compiler version and existing optimization/architecture settings for both final
binaries. No LTO, native ISA, fast-math, branching/restart changes or parameter
sweep. Freeze training inputs/options/order and profile hashes before evaluation;
do not train on Tier 1/2/3 cases or select profiles using their timing results.
Initial training candidates are LP_34_20_2 and LP_136_32_4, both OFF/MTO; confirm
input identity and completeness before the experiment preregistration.

Important preparation finding: `solve_in_child_fork` ends the child with
`_exit` (baseline `src/core/distqldpc.cc:769`). Fork support alone does not prove
solver counters reach disk. Before implementation, specify a training-only
collection route and verify nonzero, complete solver profiles. Any collection
hook must be absent from production builds and must not change scientific or
timeout behavior. Reject missing/mismatched profiles instead of suppressing
warnings or silently compiling unprofiled code. Do not benchmark instrumented
training binaries. Check host-specific compiler documentation as well; the
server and Windows GCC versions differ.

Affected cases: potentially OFF and MTO on all four Tier 1 inputs and LP340;
no claimed percentage. Risks: unrepresentative training, code-size growth,
uncovered paths, profile identity mistakes and compiler-sensitive latent bugs.
Tier 0 includes both production binaries, CSS oracle/smoke, original timeout/
bound/result behavior and required cross-repo checks. Correctness failure stops.

Expected cost: three builds (baseline, instrumented, final candidate), four
serial training solves initially budgeted at 120s each, then standard filters.
A killed/incomplete training solve invalidates this training plan; do not change
timeout/result semantics to obtain a profile. Record training cost separately
from final runtime, including any amortization claim. Build duration and effect
remain unknown. Freeze the exact training route and commands in the future
experiment record, rather than treating this proposal as an executed package.

## H-011: one core-processing scratch buffer

Hypothesis: retaining `oldset` capacity across repeated `setConflict` calls
reduces allocations without changing assignments, core contents or ordering.
Baseline `Solver.cc:4240` creates a local `vec<int> oldset`; `Vec.h` releases
capacity on destruction and retains it with ordinary `clear()`.
Calls occur in `lookaheadForRestart` and twice in `lookahead`. Allocation cost
and frequency have not been profiled; this is a concrete opportunity, not an
established bottleneck or a paper-derived technique.

Scope: move only this scratch vector's ownership to each caller invocation,
pass it to `setConflict`, clear it per use, and release it when that caller
returns. Preserve pushes, iteration, merge order and all core/lock updates.
No persistent global buffer, general vector pool, prefetch or other scratch
reuse. Audit all three call sites, non-reentrancy and absence of escaped
references before coding. If that audit requires broader state changes,
withdraw this narrow proposal rather than expand it silently.

Expected affected cases: both modes where core handling is frequent; actual
allocation counts and sampled time should determine whether it merits execution.
Unlike E003, this targets runtime core processing rather than XOR construction.
First collect a bounded diagnostic of calls, populated-buffer sizes and
allocation/time share from the baseline, with profiling separate from timings.
If reuse opportunity is negligible, reject the mechanism without expensive tiers.

Risks: stale entries, aliasing, recursive use and retained peak capacity within
one lookahead. Tier 0 checks empty/populated/merged-core paths, repeated calls,
early returns, restart cleanup, exact MaxSAT/CSS results and required hosted
checks. Compare deterministic search/core counters and WCNFs where available;
matching final answers alone is weaker evidence for this order-preserving change.
Scope would touch `Solver.cc/.h` and downstream modification documentation.
Expected cost: a few hours of engineering and a bounded baseline diagnostic,
normal builds/Tier 0, then the common 48-solve Tier 1 if justified. No runtime
gain estimate; E003's weak evidence argues for the profiling prerequisite.

## H-012: bounded further lookahead (new literature)

Source: Zhang, Li, Cherif and Li, *Enhanced Lower Bound Computation in
Branch-and-Bound for MaxSAT*, CP2026, published 2026-07-13;
key `zhang2026enhanced` in [references.bib](../references.bib).
[Official paper](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.CP.2026.60).
Read sections 2/3, Algorithms 1–3 and Proposition 6; section 3.3's RL strategy
is excluded. The method tests falsification of each literal of a weight-one
core, then merges intersecting cores and raises LB only with complete branch
coverage. This extends passive unlocking rather than proposing unlocking again.

Our proposed single adaptation: fixed size cap two, deterministic existing-core
order, after standard lookahead fails to prune. No RL, threshold tuning or
upstream solver replacement. Confirm the equivalent operation is absent in
our downstream engine before implementation; symbol searches are insufficient.
Existing `unlockReason`/`seeUnlockLits` already require careful comparison.

Hypothesis: added sound pruning saves more search than the extra propagation
cost on cases with suitable small cores, potentially OFF/MTO. E006's changed
search counters motivate investigation but do not demonstrate such cores exist.
Measure eligible-core frequency and successful additional bounds separately.

Risks: overlapping-core double counting, speculative-state rollback, implication
reasons, empty-hard-conflict branches and bound lifetime. Tier 0 must exhaustively
compare LB to exact residual optimum on small partial MaxSAT instances, including
overlaps and hard-infeasible branches, then CSS distances/bounds/timeout behavior
and required hosted checks. A paper proof does not certify our implementation.
Unresolved soundness blocks implementation/performance and requires escalation.

Expected cost: several days of soundness/implementation work, more exhaustive
Tier 0 than H010/H011, then standard filters. Solver-side changes require
MODIFICATIONS/NOTICE updates. The paper's software repository has multiple
variants; no code import or code-license approval is assumed. Preserve embedded
MaxCDCL attribution. This proposal tests our restricted adaptation, not a
reproduction or rejection of the paper's full system.

## Common future experiment protocol

Each selected experiment starts independently from baseline24572d6, records an
exact diff/commit and commands before implementation, and changes one concept.
Tier 0 precedes timing; any scientific mismatch/crash/output regression rejects
and stops. Tier 1: BB_90_8_10, GB_144_12_8, BB_108_8_10, LP_238_44_6;
baseline/candidate three times each, OFF/MTO separately: 48 serial solves.
Keep raw samples, medians, variability, scientific results and resource telemetry.
Use interleaved AB/BA/AB on the same CPU; no simultaneous sibling comparison.

Proposed lightweight budget retains 180s parent/195s watchdog per solve:
at most 156 minutes of watchdog time, usually less but not predicted. LP340
Tier 2, only after positive reproducible Tier 1 without serious regression:
12 solves, 600s/615s limits, at most123 minutes. No Tier 3 from this Brain round.
These are future experimental budgets, not changed benchmark semantics.

User capacity rule remains global spare>50%, using at most half spare capacity.
Diagnostic contention may be recorded without abort under the existing explicit
policy; label it honestly. Server corroboration and a demonstrated robust
performance decision remain necessary for adoption. Shared CI timing is never
research evidence. Keep INCONCLUSIVE if uncertainty can change the decision;
preserve failed records. Explicit exploratory tier exceptions are separately
preregistered and never turn a failed gate into PASS.

Validation of this round: code/source/history inspection and primary-source
research; documentation/link/diff checks only. No new correctness or performance
result, no scientific semantics changed, no PI action required.
